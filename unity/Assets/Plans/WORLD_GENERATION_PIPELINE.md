## Purpose

The user's full target shape for world generation, distilled into project terms and cross-referenced to the System Cards in `17`. **Not a build order** — `OVERWORLD_V0_PLAN.md` and the iteration list in §3 below govern what actually gets implemented and when. This doc exists so every later wave has a consistent picture of where it's heading, instead of each terrain feature being invented ad hoc.

Quality bar (the user's framing, kept verbatim because it's the right test):

> Не спрашивать "насколько красиво выглядит отдельный кусок terrain?" А проверять: "создаёт ли генератор естественную географию, которая сама создаёт интересные места для исследования?"

A traversal should read as *forest → hills → valley → river → bridge → village → open plain → old forest → mountain pass → lake → city*, not as undifferentiated noise.

## 1. Seed hierarchy

One `WorldSeed` forks independent named streams — changing one must not change another (`WorldSeed.Fork("vegetation")` changing must not move the mountains):

```
WorldSeed
 ├── terrain      (heightmap, macro/medium/detail shaping)
 ├── biome        (temperature/humidity/moisture bands)
 ├── river        (hydrology graph)
 ├── vegetation   (scatter density + placement)
 ├── poi          (already the W.4 fork name)
 └── settlement   (already the W.5 fork name)
```

`W.1 WorldSeed` (`unity/Assets/Scripts/World/Seed/`) already implements fork-by-name. **Known gap:** `OverworldTerrainMenu.BuildGraph` currently derives multiple values from one `"terrain"` fork via sequential `.Next()` calls (graph seed, plateau seed, mountain seed) — inserting a new noise layer in the middle would silently shift every later derived seed. Each independent concern should get its own named fork (`Fork("terrain.plateau")`, `Fork("terrain.mountain")`, …) instead of relying on call order. Fix when terrain generation moves from the Editor lab tool into real `W0.3`/`W0.4` code, not urgent for the throwaway graph-builder.

## 2. Pipeline stages → System Cards

| # | Stage | Produces | Maps to (17) | V0 status |
|---|-------|----------|---------------|-----------|
| 1 | World Layout | Continents/islands/coastline | New — not in `17` yet, out of scope until multi-tile worlds are real | Not started; V0 is one stub tile, no ocean/continent concept |
| 2 | Macro Terrain | Mountains/plains/valleys/plateaus, at 3 scales (primary/secondary/detail noise, not one octave) | `W.2 Terrain/Biome` | **Percentile-ranked + vertically compressed macro shape** — one `macroNoise` field feeds `PercentileRankGenerator` (custom node, `Assets/Scripts/World/Terrain/PercentileRankGenerator.cs`), which remaps every cell to its own rank in the field's distribution, so `BiomeClassifier`'s height bands become exact area-fraction guarantees regardless of seed (a fixed threshold on raw Perlin noise couldn't promise that - documented at length in `BuildGraph`'s history). Raw per-pixel ranking also locally steepens the field wherever the source distribution is densest (Perlin's own middle range, i.e. what should've been gentle terrain) - a `Blur200` pass (~60m, well under the biome bands' spatial scale) tames that pixel-scale jaggedness without erasing the macro banding. Area guarantee alone isn't slope/flatness, though - a rank band says nothing about how hilly it looks, and city sites need actually flat ground - so a `BiomeClassifier.PlainsElevationCap`-sized vertical compression squeezes the bottom `RankGreenMaxHeight` of ranked area (Swamp+Green) into a thin elevation slice while Highland+Mountain keep the rest, real-hypsometric-curve style; `BiomeClassifier`'s public thresholds are the compressed-elevation values this produces, derived as const expressions from the `Rank*` design-intent percentiles so the guarantee still holds after compression (monotonic transform, never reorders which cell is higher). Mountain terracing operates on the compressed field the same way (subtract the smooth local contribution, add the terraced one back, both scaled to the band's width) so it still only affects the guaranteed Mountain fraction. Tile size bumped to 1400x1400 (from MapMagic's 1000x1000 default) for more breathing room between the mountain feature and buildable plains |
| 3 | Hydrology | Watersheds, rivers, lakes; **rivers carve terrain**, not decals on top | New sub-concern of `W.2`/`W.4` | Lakes started (`GameDev.World.Water`, flood-filled from generated terrain) — rivers not started. Known residual: `WaterMeshBuilder` still occasionally draws a partial "cliff" ring inside a lake around a small dry patch at a cell boundary between two adjacent flood regions that don't share a claimed cell but sample close to the water level - not critical, deferred. Likely needs a smarter shoreline than the current per-cell/per-neighbour skirt heuristic (e.g. marching-squares contour extraction instead of grid-cell skirts) if revisited |
| 4 | Biomes | Meadow/Forest/Swamp/Highland/Mountain from **height + slope + moisture + temperature + distance-to-water**, not height alone | `W.2 Terrain/Biome` (`IBiomeSampler`) | **Height + slope + moisture, with guaranteed area fractions** — `BiomeClassifier.Classify(height01, slope01, moisture01)` against a percentile-ranked height channel (see Macro Terrain row above): bottom 10% Swamp(wet)/Meadow(dry), next 35% Forest(wet)/Meadow(dry), next 35% Forest unconditionally, next 10% Highland (new `BiomeId`) unless steep (then Mountain), top 10% Mountain - Green (Meadow ∪ Forest) is guaranteed >= 70% of the map by construction, comfortably past the "at least half the map is green" requirement. | 7 | Vegetation | Density maps per biome, then scatter (Low Poly Environment prefabs) | `W.2`/`W.4` dressing | Not started (asset ready — see `ASSET_LIBRARY_REFERENCE.md`) |
| 8 | World Features | Ruins/caves/camps/shrines as POI markers | `W.4 POI Placement` | Started — `PoiKind` list already includes ruin/camp/shrine/town approach/cave mouth |
| 9 | Roads | Lowest-cost path through terrain (slope/river/mountain aware), not straight lines | `W.5 Settlement` | Not started |
| 10 | Settlements | Location choice (flat + water + road access) → `W.5` | `W.5 Settlement` | **S6–S8:** TownApproach dry fabric + District Mix + street props (`SETTLEMENT_PROPERTY_V0.md`) |
| 11 | Districts / Plots | Multi-district parcels + GardenSquare open space + street spine + street dress | `W.5 Settlement` | **Lab through S8** — `CreateDistrictMix` + `StreetPropPlacer`; not OrganicTown |
| 12 | Buildings | Building DNA / Piece-Based Assembly | `W.6 Building/Shell`, [15](../../../15%20Procedural%20Building%20Generation.md) | Deferred |

## 3. Principles worth keeping verbatim

- **Never one noise field.** `Landmass mask + mountain mask + large noise + medium noise + biome modifiers + erosion → final height`, each layer with a stated job. This is already how `OverworldTerrainMenu`'s plateau+mountain-noise+Levels blend works; extend the same way (add layers with a reason), don't collapse back to a single Perlin call.
- **Terrain masks are data, not throwaway locals.** Height, temperature, humidity, moisture, slope, distance-to-ocean, mountain-influence, forest-influence, river-influence — worth keeping as named channels (the `DirectMatricesOutput200` mechanism already proves this is wireable) so biome/material/vegetation/road rules can all read the same maps instead of each re-deriving their own.
- **Rivers reshape terrain.** Path → valley → depression → bed → water, in that order. A blue spline laid on unmodified terrain is not hydrology.
- **Biome is not just a texture switch.** It should also drive terrain shape tendencies, vegetation density, and (later) POI placement rules — see `W.2`'s relation to `W.4`/`W.6` dressing.
- **Roads are pathfinding, not lines.** Lowest-cost path respecting slope, rivers (bridges), and mountains (passes) — never straight through a mountain.
- **Settlements are shaped by terrain**, not a flat square with houses dropped on it — matches `W.5`'s "layout intents: road hints, plot footprints, district tags" wording already in `17`.
- **Chunk generation must be a pure function of world coordinates** (`Height = f(worldX, worldZ, seed)`), never local-to-chunk coordinates, or neighboring chunks won't agree at the border. Already how `ChunkCoord` (`W0.2`) and the MapMagic `DirectMatricesHolder` world-space queries (`W0.3`) are built — keep it that way for every future sampler.
- **Generation is not persistence.** Regenerable structure (heightmap, biome bands, vegetation placement) is never saved; only player-caused deltas (felled tree, built structure) are. Matches `X.3 Save System`'s existing "never dump regenerable chunk meshes" rule.

| 09 | Roads (graph + terrain cost + river crossings + mountain passes) | **First slice done, rebuilt for scale** — `RoadNetworkMenu` connects the `PoiDemoScenario` markers `PoiMarkerMenu` visualizes into a minimum-spanning-tree graph (`RoadNetworkBuilder`), each edge routed with a slope/biome/water-aware grid A* (`RoadPathfinder` + `RoadCost` + `RoadCostSampler`, `Assets/Scripts/World/Roads/`) — steep slope and Swamp/Mountain biomes cost more per meter (so a gentle mountain saddle beats a steep shortcut, satisfying "passes, not straight through peaks"), submerged ground is impassable at the per-point level, but `RoadPathfinder.TryBridge` can skip a short span of it (up to `RoadCost.MaxBridgeSpanMeters` = 120m) as one long edge priced by real distance × `RoadCost.BridgeCostPerMeter`, so a narrow lake neck/inlet gets bridged instead of always detouring - a wide lake still has no route across it (no real river/strait system exists yet, matching Iteration 05's still-pending river carving). Segments now render as real geometry (`RoadMeshBuilder`, `RoadMeshBuilderTests`) instead of `LineRenderer` debug lines — a ribbon strip per segment with width applied as a horizontal offset off the path's flattened tangent (so it doesn't pinch on steep ground) and UVs tiled by actual travelled distance (not per-sample-step), textured with MapMagic's Dirt diffuse (`Assets/MapMagic/Demo/LandTextures/Dirt.tif`) since no dedicated road texture exists yet. Fixed a staleness bug: `OverworldTerrainMenu.GenerateInternal`/`ClearTerrain` cleared Vegetation/POI on regenerate but never `RoadNetworkMenu`'s output, so a route built against an earlier terrain/water layout could survive a full regenerate and end up visibly crossing a lake the new generation placed where the old dry ground used to be - both methods now also call `RoadNetworkMenu.ClearRoadNetwork()`. Fixed a second, seed-independent bug in the same family: `WaterZoneMenu` insets its own sampling by a margin from the raw tile edge (so `LakeBasinFinder`'s neighbour lookups never read out-of-bounds height), which means a lake that visually reaches the tile edge can have its flood mask stop just short of it - POI placement and road routing had no such margin, so a lake-adjacent border strip with no flood data read as free, dry ground and a road could hug the tile boundary in a straight line across what still looked like open lake. Centralised the margin as `OverworldTileChunks.DefaultMarginMeters` (`Assets/Scripts/World/Streaming/OverworldTileChunks.cs`, `OverworldTileChunksTests`) - `WaterZoneMenu`, `PoiMarkerMenu`, `RoadNetworkMenu`, and `SettlementOverworldMenu` all now agree on the same tile-edge exclusion band (POI candidate chunks filtered by chunk-center position, and the road pathfinding grid itself shrunk to stay inside it). **Bridges added** — a bridge span (detected in `RoadNetworkMenu` as an unusually long jump between consecutive reconstructed-path points, since `TryBridge` skips the submerged cells between entirely rather than recording them) renders as the actual Low Poly Village bridge prop (`PT_Wooden_Bridge_02.prefab`) tiled edge-to-edge along the gap, instead of the plain dirt ribbon; the ribbon itself needs no special-casing since a straight line between two above-water shore points mathematically stays above that same constant water level throughout. EditMode coverage extended: `RoadPathfinderTests`/`RoadNetworkBuilderTests` now cover both "narrow gap bridges" and "gap wider than `MaxBridgeSpanMeters` finds no route". Retuned after real-world testing showed bridges essentially never appeared: `BridgeCostPerMeter` 3.5→2 and `MaxBridgeSpanMeters` 120→200 - the original values made almost every detour cheaper than almost every bridge, and 120m rarely lined up with an actual narrow point on the lake-pit generator's fairly round, up-to-~500m basins. `RoadNetworkMenu`'s completion log now also reports a real bridge count per generation, so "is bridging firing at all" is answerable without opening the Scene view. **Bridge module rotation fixed** — `PT_Wooden_Bridge_02`'s deck runs along its local +X axis, not +Z, so `Quaternion.LookRotation(direction, up)` (which aligns local +Z to the target) landed every module rotated 90° off the crossing direction, standing sideways/parallel instead of end-to-end; fixed with an added `* Quaternion.Euler(0f, -90f, 0f)` correction (the exact sign is a best guess from indirect prefab-bounds evidence, not yet visually confirmed). **Mountain grade now genuinely hard-capped** — `GradeMultiplier` previously only ever multiplied cost, never blocked, so a step steeper than any real road could climb still produced *a* path (A* always returns the least-bad reachable option), rendering as a technically-connected but physically-impossible near-vertical line. Added `RoadCost.MaxWalkableGrade` (0.6, ~31°) as a genuine `float.PositiveInfinity` cutoff, reusing the same "infinite cost blocks the step" mechanism already proven for submerged water - a step steeper than this is refused outright, forcing a genuinely walkable detour (or an honest "no route for this pair" via the same repair-pass machinery that already handles water-blocked pairs) instead of drawing an unusable line. First-attempt threshold, not yet visually confirmed; true switchback/ring-around-the-peak routing still doesn't exist - this only stops the pathfinder from accepting a cliff-face shortcut; a good detour still has to exist in the KNN candidate graph for the edge to succeed at all.

**Hugs the real terrain instead of floating/clipping, and carves a worn-track groove.** The rendered ribbon used to connect the sparse ~25-35m pathfinding waypoints with straight lines, cutting through any dip or rise in between - `RoadPathDensifier` (`RoadPathDensifierTests`) re-samples each ordinary run at a fine ~4m interval first, and `RoadNetworkMenu` re-raycasts ground Y at every dense point, so the mesh now follows the actual undulation. `RoadTerrainCarver` additionally presses a groove into the terrain's real heightmap along every such run before that raycast pass runs - centuries of wheels settling a path into the ground, not a road resting on top of it - reading the whole heightmap once, applying every run's carve to an in-memory copy measured from one consistent original, then writing back once. First pass (0.5m deep, `RoadWidthMeters+3` wide) turned out invisible in practice - the heightmap/alphamap is coarse enough (a few metres per texel on a ~1400m tile) that it barely registered as more than a couple of pixels - raised to a genuine holloway depth (1.4m, `RoadWidthMeters+10.5` wide) with a `MinRadiusPixels` floor so a groove can't under-resolve to a single pixel regardless of the map's actual resolution. `RoadTerrainCarver` also paints a matching "worn dirt" strip into the terrain's alphamap over the same footprint (reusing the same scaled Dirt layer `OverworldTerrainMenu.BuildGraph` already paints onto wet-low ground, so the groove reads as trampled bare ground, not just a dip in the grass) - reads the whole alphamap once, computes each pixel's max influence across every centerline point, then renormalizes every other layer's weight down proportionally in one pass so the total stays 1. Known gap: neither pass has any memory of a prior carve, so rebuilding roads in place (without regenerating terrain first) carves/paints a second time on top of the first - regenerating terrain always gives a clean, uncarved heightmap/alphamap, which is the reliable way to get a fresh result.

**Mountain climbs now favour a longer traverse over a short, steep direct ascent** ("switchback" behaviour), instead of going nearly straight up. `RoadCost.Evaluate`'s existing slope01 term is a per-POINT reading (how steep the ground is right here) and can't by itself distinguish "walking along a mountainside's contour" from "walking straight up it" - both read equally steep regardless of travel direction. `RoadPathfinder.TryFindPath` gained an optional real-elevation (metres) delegate; when supplied, each ordinary step's cost is additionally scaled by `RoadCost.GradeMultiplier` using the real rise-over-run of that specific edge - cubic growth once grade exceeds `MaxComfortableGrade` (15%) makes a direct climb dramatically pricier than a longer, gentler route, without ever literally blocking a step. `RoadNetworkMenu` wires this from the same normalized height channel `IBiomeSampler.SampleHeight` already exposes, scaled by `mapMagic.globals.height` into real metres. This produces a grid-search approximation of a switchback (long gentle traverses connected by short steeper pinches, following whatever lateral slope variation - including the Highland/Mountain terracing from Iteration 01 - the terrain actually has), not an engineered hairpin-turn geometry; a true geometric switchback layout would be a further follow-up. EditMode coverage: `RoadCostTests` (`GradeMultiplier`), `RoadPathfinderTests` (grade increases reported cost; a heavily-penalized direct climb loses to a much longer gentle detour; omitting the height delegate keeps the old direct-route behaviour, unchanged for every existing caller). Still no river crossings (no rivers exist yet) and no other road props (signs, fences, etc.) |
| 10 | Settlements (location → type → districts → road network) | Property lab through S8 (`SETTLEMENT_PROPERTY_V0.md`: District Mix + GardenSquare + street props + overworld dry place); terraces / TownDress deferred. **Linked to the road network** — `SettlementApproachBinder.TryCreateDryFabricNearApproach`'s dry-ground search can move the fabric up to ~192m (`DrySearchRingMax * DrySearchStepMeters`) from its raw TownApproach POI marker, which previously left `RoadNetworkMenu` routing to a coordinate the settlement no longer occupied. `SettlementOverworldMenu` now drops an `OverworldSettlementAnchor` (`Assets/Scripts/World/Settlement/`) recording the fabric's real landing position, and `RoadNetworkMenu` substitutes that position for the matching TownApproach marker when building its node list, so the road actually reaches the town. Only works when Settlement placement runs before Roads - `OverworldPipelineMenu.RunRemainingSteps` reordered accordingly (Settlement now comes before Roads); running `Build Road Network` standalone without an existing settlement still falls back to the raw marker position, unchanged from before |

| 12 | Streaming (chunks, async, LOD, unload) | `ChunkCoord` math done; async/LOD not started |

**Where we actually are:** Iterations 01 and 03-09 done for V0 scope (terrain shaping incl. Highland/Mountain terracing, multi-scale noise, height+slope+moisture biomes with guaranteed area fractions, terrain-derived Water Zones, 6-layer terrain painting, density/slope-aware vegetation, quota-scaled POI with real props, and a bridged, scalable road network), Iteration 10 (Settlements) through the property lab and linked to the road network. Still open: Iteration 02 (Landmass/ocean, deliberately deferred until multi-tile worlds), river carving (part of Iteration 05, lakes only so far), temperature/distance-to-water biome axes, POI Director lifecycle (Q.3 - markers are still placed props, not live gameplay objects), and Iteration 11 (Buildings, deferred by `15`).

**One-button pipeline:** `OverworldPipelineMenu` (`Assets/Scripts/Editor/OverworldPipelineMenu.cs`) exposes `GameDev/Overworld/Build Full Overworld (Random Seed)` / `(Default Seed)` and `Clear Full Overworld`, running every step above (terrain+water → POI → vegetation → roads → settlement) in one call instead of clicking each per-step menu item in order. **Whenever a future iteration adds a new Overworld menu step (or a Clear* counterpart), add one call to `OverworldPipelineMenu.RunRemainingSteps` (and `ClearFullOverworld` if applicable)** so this button keeps producing the full, current demo instead of silently falling behind what the individual menus can do.
